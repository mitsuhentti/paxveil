# PAXVEIL — инженерный кейс для портфолио

PAXVEIL превращает файл Python-зависимостей в сохранённый отчёт с источниками и историей, помогает сравнить обновления и отслеживает изменения через Telegram. Веб и бот работают поверх одного owner-scoped API. Цель кейса — показать обработку неоднородных внешних данных, устойчивые фоновые задания и полезное пользовательское представление результата.

## Проблема и результат

Номер версии и отдельная запись CVE не дают разработчику готового решения: advisory имеют разные identifiers/aliases, источники доступны не всегда, а обновление одного пакета меняет транзитивный состав. PAXVEIL сохраняет проверяемый инвентарь, объединяет связанные advisory, объясняет приоритет и повторно проверяет реально разрешённые варианты обновления.

В реальном испытании пяти публичных закреплённых зависимостей система получила 12 находок после deduplication. FixLab Balanced и Maximum Coverage разрешили пять пакетов и вернули ноль известных находок при последующем OSV-запросе; Minimal Change сообщил об отсутствии достаточных оснований для подходящей стратегии. Fire Drill подтвердил совпадение `CVE-2024-35195` с сохранённой версией `requests`. Эти результаты привязаны к дате источников и не доказывают поведение приложения после обновления.

## Что демонстрирует Data Engineering

| Решение | Проверяемое проявление |
|---|---|
| Модель данных | PostgreSQL-сущности users/projects/scans/packages/versions/dependencies/advisories/findings, FK, индексы и уникальность |
| Provenance и история | Immutable JSON reports, content hashes и timestamps публичных source snapshots, история состояния findings |
| Инкрементальная обработка | Watch повторно сканирует сохранённый файл, сравнивает надёжные baseline и создаёт события по изменениям |
| Качество | ETL-проверки orphan records, дубликатов, диапазона priority и полноты завершённых scans |
| Аналитика | SQL views `scan_risk_metrics` и `notification_delivery_metrics`, отдельная команда чтения metrics |
| Устойчивость | Очередь PostgreSQL, SKIP LOCKED, lease/claim tokens, retry/backoff, атомарное сохранение результата |
| Неоднородные источники | OSV aliases/affected ranges, PyPI metadata, deps.dev cross-check, EPSS date, CISA KEV; null/partial сохраняются явно |

Airflow, dbt, Redis и Celery не добавлены ради перечня технологий. Для проверенного локального масштаба PostgreSQL-очередь и отдельный scheduler выполняют реальные задачи без дополнительных системных сервисов. Эти ETL-команды можно позднее запускать из внешнего orchestrator.

## Что демонстрирует Backend Development

FastAPI отделяет короткие пользовательские запросы от долгих scan/FixLab jobs. Авторизация использует hash-only sessions и PBKDF2 пароли; каждый объект ограничен владельцем. Web-to-Telegram linking потребляет короткоживущий одноразовый код. Уведомления проходят через outbox с дедупликацией, quiet hours, thresholds и журналом доставки.

Загрузки ограничены форматом, размером и количеством зависимостей. Manifest не исполняется. Источники имеют фиксированные разрешённые HTTPS hosts; FixLab разрешает wheel metadata через proxy с доступом только к официальным PyPI hosts. Неполный OSV lookup не становится чистым отчётом. CVSS, EPSS и сведения об известной эксплуатации имеют разные значения в модели и интерфейсе.

Native-сценарии требуют PowerShell 7. Технический стек: Python 3.11, FastAPI, Pydantic, SQLAlchemy, Alembic, PostgreSQL, httpx, uv, aiogram; Next.js, React и TypeScript. Есть Compose, lock-файлы и workflow GitHub Actions. Их фактическая проверка отражена в [TEST_RESULTS.md](TEST_RESULTS.md); конфигурация CI не означает исполненного remote CI.

Для демонстрации после [локального запуска](DEPLOYMENT.md):

1. Открыть веб, создать аккаунт и загрузить `examples/browser/requirements.txt`.
2. Дождаться настоящего задания; открыть source completeness, advisory и ограничения неполного транзитивного состава.
3. Открыть граф, изменить статус находки, показать сохранённую историю.
4. Запустить FixLab, сравнить целевые версии, реальное разрешение и последующую OSV-проверку. Объяснить, что приложение после обновления ещё требует своих тестов.
5. Выполнить Fire Drill с `CVE-2024-35195`; показать совпадение и ссылку на источник.
6. Включить Watch, сохранить тихие часы и затем выключить мониторинг у демонстрационного проекта.
7. После Telegram human acceptance связать аккаунт, открыть проект в боте, отправить файл и показать общий отчёт.
8. Штатно остановить/запустить приложение; сверить проекты, историю и подписки с [фактическим результатом restart test](RUNTIME_VALIDATION.json).

Публичные lock-примеры не устанавливаются в окружение. Контролируемые тестовые advisory используются только в tests, отдельно от живых отчётов. Для публичного показа исключить `.env`, runtime, реальные идентификаторы пользователя и приватные manifests. Скриншоты в репозитории сделаны по тестовым аккаунтам и публичным зависимостям.

## Формулировки для резюме

**Data Engineer:** «PAXVEIL — локальная платформа анализа Python-зависимостей: интеграция OSV/PyPI/deps.dev/EPSS/CISA, нормализованная PostgreSQL-модель, исторические snapshots и provenance, инкрементальный Watch, SQL-витрины и ETL quality checks. Устойчивые задания используют leases, retries и claim fencing; результаты подтверждены живыми API-отчётами».

**Backend Developer:** «PAXVEIL — FastAPI/PostgreSQL-сервис с owner-scoped авторизацией, асинхронным сканированием, моделированием обновлений через uv, Fire Drill и aiogram-клиентом. Реализованы одноразовая привязка Telegram, notification outbox, настройки доставки, file limits и ограниченный сетевой доступ resolver; проведены автоматические и браузерные проверки».

Проект создан в совместной сессии с workspace. В портфолио следует описывать личный вклад владельца по факту: постановка требований, проверка сценариев, принятые инженерные решения и последующие изменения. Эти формулировки описывают систему и не приписывают человеку не выполненную им работу. История Git отражает реальные изменения с честной атрибуцией.

## Следующий инженерный этап

Завершить живую Telegram-проверку загрузки, привязки, отчёта и Watch: владелец уже подтвердил меню после `/start`. Проверить Compose и backup/restore в отдельной среде; добавить deployment quotas/retention/shared rate limits и проверить PostgreSQL concurrency под несколькими worker. Для заявлений о production readiness потребуются публичная инфраструктура, наблюдаемость и результаты эксплуатации. Повторная подготовка существующего runtime прошла дважды с сохранением кластера и токена. Финальная обычная остановка PostgreSQL вне изоляции Windows и новый запуск прошли успешно; hash QA-проекта, одного scan, трёх статусов и подписки сохранился. Ранее также проверен force-stop/WAL recovery собственного dev-кластера. Полный fresh bootstrap ещё не проверен. [Операционные проверки](OPERATIONS_VALIDATION.md) описывают эту границу. Текущее состояние и ограничения указаны в [PROJECT_STATUS.md](../PROJECT_STATUS.md).
